# Token 用量审计：研究依据与可验证范围（2026-11-04）

## 为什么大任务不等于真实计量

总量大可以减小固定开销、K/M 舍入对比值的影响，但不提供新的可信来源。
例如输入上报 y = x + 3000，短输入的 y/x 会很高；这与 y = 3x 是两种情况。
至少三档长度、每档重复，并把固定项和增量分开，才有机会区分二者。
这里 x 必须有可信计数；字符数除以三只是一种估算，不能证明收费倍率。
隐藏推理、网关追加上下文、重写或截断仍不可由可见回答完整还原。

## 已核验来源与取舍

- [Veridrop OpenAI token_billing 源码](https://github.com/canarybyte/veridrop/blob/e87ed92ae37250f87a6503b321c0bc7109618008/src/relay_detector/protocols/openai/detectors/token_billing.py)：短/长提示差分、usage 加法和流式一致性；有官方 Key 时另采三轮参考。源码明确不证明供应商账单。
  本次采纳“受控差分”的思路，沿用 RelayLens 自身的计数/限时机制；不照搬固定 apple 增量窗口和很小的推理输出预算。
- [RelayRadar 计费分析源码](https://github.com/AetherCore-Dev/relay-radar/blob/cdf51e8593b7f56102402708f901a2992c706c50/packages/core/src/analyzer/index.mjs)：短题手写 Token 区间与输入开销启发式。固定区间不适用于未知新模型，隐藏推理等也会影响输出计数；未移植其“公平分”。
- [PALACE 论文](https://arxiv.org/html/2508.00912v1)：用适配后的审计模型预测隐藏推理长度。需要目标服务相关数据、训练及校准；预测不是真实账本。本次未把未经校准的 Qwen 猜测当作该论文实现。
- [CoIn 论文及代码入口](https://openreview.net/forum?id=QfgD2HkEnV)：用 hash tree 和 embedding 相关性验证隐藏 Token，需要服务端/审计方参与。普通中转 API 不提供这些证据，无法只安装客户端就启用同等验证。
- [Linux.do 社区讨论](https://linux.do/t/topic/2199605?page=2)：有人报告排行榜和实际使用不一致，也有人担心检测提示被特别路由。此处仅作为设计测试随机化与透明证据的线索，不据此断言任何平台造假。

## 本次实现

向导在原有“回车开始”处增加 T=用量专项，或 CLI 使用 --usage-only。
默认生成三种长度的随机英文字符块（256 / 2048 / 16384 个主体字符，空格及说明另计），每种相同请求重复三次，顺序随机但 seed 可复现。
这是约六万余输入字符的默认探针设计，不宣称等于多少真实 Token；无需先消耗几百万 Token。

复用原有 180 秒并行采集、停止回收和报告功能。原始能力快检保持原样；专项不运行能力题，不调整思考档、不强行压缩输出预算，也不生成能力等级。
计数缺失、请求失败或未返回 OK 的探针不按零用量或欺诈计分。

新增证据检查：

1. usage 字段的加法与缓存/推理子集约束。
2. 相同 payload 的输入总量是否重复稳定；显示缓存读数变化，但不把缓存重复计入总量。
3. 至少三组重复、六次可用观测及足够长度跨度后，说明输入增量可比性。
4. 精确官方计数可用时沿用现有斜率/固定项诊断。没有独立基准时清楚标注“真实倍率仍缺独立基准”。
5. 显示已上报的隐藏推理占输出比例，解释为何可见短回答也可能有较大输出量。这个比例仍是服务方声明。

“明显波动”使用范围超过 max(2 Token, 组内输入中位数的 1%) 的产品提示阈值；不是统计置信度或造假概率。
斜率同样只是诊断。即使所有检查正常，仍不证明隐藏推理、账单价格或上游真实消耗。
甲乙丙丁戊继续只表示有可比参考时的任务消耗，不把稳定性分数替代消耗等级。

## 取得更强证据

如有官方账户，可用 --official-count-key-env 指定仅发给官方计数接口的环境变量。
这只计量提交内容，无法看见中转追加内容；Claude 官方计数是估算，不能升级成精确证据。
网关自己提供的 count_tokens 不属于独立来源。
要验证完整上游成本，仍需要独立官方日志/账单、可核验的服务端证明，或公开且经过目标模型校准的统计基准。
